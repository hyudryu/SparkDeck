API & client examples

Point any OpenAI client at http://<host>:7878/v1.

How routing works

The controller exposes an OpenAI-compatible API on port 7878. GET /v1/models returns every model the controller knows about — both vLLM containers (running or stopped) and Ollama models. The model field you send in /v1/chat/completions determines which backend handles it:

  • vLLM model (HF repo id, e.g. RedHatAI/Qwen3.6-35B-A3B-NVFP4) → controller finds the matching managed container. If the GPU is full it evicts the least recently used running model, starts the target if it's stopped, waits for /health, then streams the request through. Subject to a 5-minute load timeout.
  • Ollama model (prefixed with CLOUD , e.g. CLOUD llama3.1:8b) → controller strips the prefix and forwards directly to the Ollama daemon. Ollama loads on demand internally; no container swap.

By default up to two vLLM containers may run concurrently (configurable in Settings). Requests for the same model run in parallel; requests for different models are queued and dispatched as GPU memory allows. Two cloud requests always run in parallel.

Python · openai SDK (pip install openai)

from openai import OpenAI

client = OpenAI(
    base_url="http://<host>:7878/v1",
    api_key="sk-noauth",   # any non-empty string; the controller ignores it
)

# vLLM model
resp = client.chat.completions.create(
    model="RedHatAI/Qwen3.6-35B-A3B-NVFP4",
    messages=[{"role": "user", "content": "Hello"}],
    max_tokens=64,
)
print(resp.choices[0].message.content)

# Ollama model — note the CLOUD prefix
resp = client.chat.completions.create(
    model="CLOUD llama3.1:8b",
    messages=[{"role": "user", "content": "Hello"}],
)
print(resp.choices[0].message.content)

Python · streaming

stream = client.chat.completions.create(
    model="RedHatAI/Qwen3.6-35B-A3B-NVFP4",
    messages=[{"role": "user", "content": "Tell me a joke."}],
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content or ""
    print(delta, end="", flush=True)

Direct → vLLM container (advanced)

Each running vLLM container also exposes its own OpenAI-compatible API on a host port in the 8000–8099 range — visible in the Models tab or via GET /api/state → containers[].port. Use this if you want to bypass the controller's eviction/load logic and talk straight to vLLM. Skips swap handling, so the model must already be running. 

curl -s http://<host>:<container-port>/v1/chat/completions \
  -H 'content-type: application/json' \
  -d '{"model":"<HF id>","messages":[{"role":"user","content":"Hello"}]}'

Model lifecycle (vLLM only)

  • By default up to two vLLM containers can share the GPU concurrently (configurable via Max concurrent models). A request for another model only stops the least recently used running model when the GPU is full.
  • Cold-load timeout: 5 minutes. If the model takes longer (large MoE / NVFP4 rebuilding CUDA graphs), the request returns 504 while the load continues in the background — retry once it's ready.
  • Idle auto-stop: after of no inference traffic (configurable in Settings; 0 disables). Direct hits to a container's port also keep it alive — the idle monitor reads vLLM's /metrics request counter.
  • The next request for a stopped model transparently restarts it; weights stay in the host's page cache, so warm reloads are much faster than the first cold load.
  • Cross-backend mutual exclusion. vLLM, Unsloth, and Ollama never share the GPU at once. Booting or starting a vLLM container first unloads any loaded Unsloth model and runs ollama stop on every model Ollama has loaded; loading an Unsloth model first stops running vLLM containers and unloads Ollama models. Eviction is best-effort and runs before the requested action — one backend being unreachable won't block the others.
